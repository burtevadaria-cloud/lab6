### Задание 3. Нагрузка

Для проверки автоматического масштабирования с `bastion` запускался Bash-скрипт, отправляющий HTTP-запросы на DNS-имя балансировщика в течение 600 секунд.

```bash
ALB=<DNS-имя балансировщика>
end=$((SECONDS+600))
while [ $SECONDS -lt $end ]; do
    curl -s -o /dev/null "http://$ALB/"
done
```

## 4. Ответы на контрольные вопросы

**Какой ответ вернул балансировщик и почему? Зачем ему подсети в двух зонах?**  
До регистрации серверов балансировщик вернул HTTP 503 (Service Unavailable), поскольку целевая группа была пустой. Подсети в разных зонах доступности обеспечивают распределение запросов и отказоустойчивость: при отказе одной зоны балансировщик может направлять запросы на исправные серверы другой зоны.

**Чем группа Auto Scaling отличается от целевой группы? Почему в шаблоне нет подсети?**  
Auto Scaling Group управляет жизненным циклом EC2: создаёт, заменяет и удаляет экземпляры, поддерживая необходимую ёмкость. Target Group содержит зарегистрированные цели, на которые ALB направляет запросы, и определяет их работоспособность. Подсети задаются в Auto Scaling Group, а не в шаблоне запуска, чтобы один шаблон можно было использовать для размещения серверов в разных зонах.

**Сколько серверов запустила группа и почему не больше четырёх?**  
Изначально группа поддерживает два сервера, а при высокой нагрузке может запустить ещё два. Фактическое максимальное количество экземпляров во время теста: [указать по вкладке Activity]. Группа не увеличивает ёмкость выше четырёх из-за ограничения Maximum capacity = 4.

**Почему метрика упала после запуска новых серверов, хотя запросов не стало меньше? Почему группа добавляет серверы быстрее, чем убирает?**  
Метрика `RequestCountPerTarget` отражает количество запросов на одну цель: после добавления серверов общая нагрузка распределяется между большим количеством экземпляров. Увеличение ёмкости выполняется быстрее, чтобы избежать перегрузки приложения. Уменьшение происходит осторожнее, чтобы кратковременное снижение нагрузки не привело к преждевременному удалению серверов и повторному масштабированию.

**Почему сессии нельзя оставить в файлах, когда серверов несколько?**  
При локальном файловом хранении сессия доступна только на том сервере, где она была создана. Если следующий запрос поступит на другой EC2 или исходный экземпляр будет удалён, пользователь может потерять авторизацию. DynamoDB позволяет всем серверам работать с общими сессиями.

**Зачем Node.js нужен initialized: true?**  
Для библиотеки `connect-dynamodb` параметр `initialized: true` означает, что таблица уже создана и хранилищу не нужно пытаться создавать или инициализировать её самостоятельно. Благодаря этому приложению достаточно разрешений на операции с элементами таблицы без дополнительных прав на управление таблицами. В моём варианте PHP OOP этот параметр не используется.

**Почему Elastic IP больше не нужен? Почему у всех серверов группы одинаковые .env и секреты?**  
Пользователи обращаются к постоянному DNS-имени Application Load Balancer, а не к IP-адресу конкретного экземпляра EC2. Серверы запускаются из одного AMI и используют одинаковую конфигурацию, чтобы обращаться к одним и тем же RDS, S3 и DynamoDB. Благодаря этому любой экземпляр может обработать запрос пользователя независимо от того, где была создана его сессия.

**Что станет с проверкой /health, если базу остановить?**  
Проверка `/health` приложения проверяет доступность основной базы данных, поэтому при остановке RDS она не сможет успешно завершиться. После установленного количества неудачных проверок ALB пометит цели как Unhealthy. Если проверки ELB включены в Auto Scaling Group, группа может начать заменять экземпляры, однако замена EC2 не устранит недоступность общей базы.

**Пришлось ли входить заново, когда группа добавляла или удаляла серверы? Почему?**  
При переключении между экземплярами повторный вход не требуется, пока пользовательская сессия действительна. Браузер передаёт идентификатор сессии в cookie, а любой сервер приложения получает соответствующие данные из общей таблицы DynamoDB. Поэтому добавление или удаление отдельного EC2 не должно приводить к потере авторизации.

**Как проходит запрос от браузера до базы и таблицы сессий?**  
Браузер отправляет HTTP-запрос на DNS-имя ALB, который выбирает цель из Target Group и направляет запрос на EC2 приложения. PHP получает данные сессии из DynamoDB по идентификатору из cookie и при необходимости обращается к PostgreSQL в RDS через `db.timecapsule.internal` на порту 5432. После обработки запроса приложение сохраняет изменения сессии в DynamoDB и возвращает ответ через балансировщик.

**Чем проверка балансировщика отличается от проверки группы Auto Scaling?**  
Балансировщик проверяет доступность HTTP-эндпоинта `/health` и определяет, можно ли направлять запросы на конкретную цель. Auto Scaling следит за состоянием экземпляров EC2 и, при включённых проверках ELB, учитывает состояние целей балансировщика, чтобы заменять неисправные серверы. Таким образом, ALB управляет маршрутизацией, а Auto Scaling — жизненным циклом экземпляров.

**Что произойдёт при отказе зоны eu-central-1a?**  
ALB сможет направлять запросы на исправные серверы в `eu-central-1b`, а Auto Scaling попытается восстановить необходимое количество экземпляров в доступной зоне. Сессии в региональной таблице DynamoDB останутся доступны независимо от отказа отдельного EC2. Однако основная база RDS в конфигурации Single-AZ остаётся зависимой от своей зоны: при её отказе приложение не сможет полноценно работать до восстановления базы.

## Вывод

В ходе лабораторной работы изучены Application Load Balancer, EC2 Auto Scaling и масштабирование по метрикам CloudWatch. Для TimeCapsule реализовано общее хранилище PHP-сессий в Amazon DynamoDB и подготовлена инфраструктура запуска приложения на нескольких EC2. Такая архитектура позволяет распределять нагрузку между экземплярами и сохранять авторизацию пользователей при смене серверов, при этом доступность всего приложения по-прежнему зависит от основной базы RDS.
